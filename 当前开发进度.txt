- 接入：OfflineMtEngine 实现TranslationEngine（名称"离线翻译"）append在引擎列表末尾——在线全失败自动兜底，截图菜单/当前翻译源可手动选中；翻译历史自动记录

## 2026-09-06 离线翻译 KV cache（第十一轮，搁置项继续）
- 解码器切换为 decoder_model_merged_quantized.onnx（If双分支图）：首步 use_cache_branch=false，后续步仅喂各束最新token + past缓存——消除每步全量重解码
- 关键发现：merged 导出的 present 输出含 decoder.*（自注意力，正确增长）与 encoder.*（cross-attention KV）两组，且 **true 分支的 encoder present 是空张量（batch=0）**——处理为两组分离：decoder 组每步更新+按束重排；encoder 组仅首步取值，之后恒定回喂（cross KV 不随步变化）、只随 beam 父束复制
- past 布局实测 [batch, heads, seq, head_dim]（元数据 [-1,8,1,64]，seq 动态维声明为字面1）；首步零长度 past 按元数据构造（seq=0）
- beam 重排：每步选择后按父束索引 gather 各层 KV 行（Row主序按 batch 维切分复制）
- 实测：三方向正确性保持；首次翻译 4.2s（含会话加载）、纯推理 1.9s/短句——短句场景与全量重解码相当（If 图开销抵消部分收益），长句/多段场景受益显著；会话加载为进程内一次性成本

## 2026-10-12 快捷键截图"要点一下鼠标才出选框"（第四十八轮，v0.4.17）

### 现象
用户：用快捷键触发截图翻译后，约 **80%** 的情况要先用鼠标点一下才出现选框。

### 根因（第 36 轮改动的副作用）
- 第 36 轮为根治桌面图标闪烁，把截图窗口显隐从 `show/hide` 换成**移出屏幕** `(-32000,-32000)` 待命
- Chromium 的**原生窗口遮挡检测**（`CalculateNativeWinOcclusion`）判定"不在任何显示器上"的窗口为被遮挡 → renderer 后台化 → **合成器停止产帧**、rAF/定时器节流
- `trigger_screenshot` 里 `SetWindowPos` 用的是 `SWP_NOMOVE`（不移动窗口），`show()` 对已显示窗口是空操作 → **事件发出时窗口仍在屏幕外**；真正的归位发生在前端事件回调的 `moveOnScreen()` 里
- 结果：state 已更新但画不出帧，要有输入事件（鼠标点一下）才唤醒 renderer。间歇性（80%）来自遮挡检测的轮询时机

### 修复
1. `main.rs` 的 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 补上 `--disable-features=CalculateNativeWinOcclusion`，并加 `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding --disable-background-timer-throttling`——屏幕外待命不再被当作后台
2. `trigger_screenshot` **先把窗口移回屏幕内**（主屏原点，与前端 `currentMonitor()` 缓存的 `monitorPos` 同坐标系，前端随后的 `moveOnScreen` 是同点幂等移动，不产生二次跳动），再 `show → focus → emit`，消除"事件先于画面"的竞态

### OPUS-MT vs NLLB-200 实测对照（用户机器，真实模型，en→zh）

用户已下载 NLLB-200（865MB）并把 `offline_model` 切到 `nllb-200`、`current_engine` 设为"离线翻译"。
用 `diag_offline_mt_degenerate_input`（已扩展为同时跑两个模型）实测：

| 输入 | OPUS-MT（77M） | NLLB-200 蒸馏（600M） |
|---|---|---|
| Mini Map and Mini Map test | 47字 / 2.47s / **完全乱码** | 11字 / **10.36s** / "迷你地图和迷米地图测试" ✅ |
| Mini Map test | 34字 / 1.01s / 乱码 | 6字 / 2.76s / "迷你地图测试" ✅ |
| Hello world, this is a test. | 15字 / 0.54s ✅ | 10字 / 4.32s ✅ |
| The weather is nice today. | 23字 / 1.06s（有重复） | 8字 / 3.88s / "今天的天气很好." ✅ |
| One or more mods caused the game to crash on launch. | 23字 / 0.74s ✅ | 17字 / **8.25s**（尾部"崩溃"被截） |
| Please disable some mods and restart the game to see if it works. | 36字 / 1.09s | 22字 / 8.35s ✅ |

**结论**：NLLB 质量是碾压性的（连 OPUS 完全译不对的 "Mini Map" 都基本正确），但**慢 4–8 倍**。
慢的根因不是模型本身，而是当前实现走的是**非 merged 解码器 + 每步全量重解码**（O(n²)）——
第 25 轮因 merged 版 KV cache 导出差异回退，第 29 轮改成非 merged 才修好退化。
**修好 merged 解码器 + KV cache 是单点收益最大的一步**（预期 5–10×），另外仓库里现成有
`decoder_model_merged_q4.onnx` / `encoder_model_q4.onnx`（4bit，体积减半）可作备选。

**内存代价**：NLLB 常驻约 1.2GB（启动后 5 秒的预热就把 600M 模型加载进内存，
即使不使用离线翻译也占着）——这是"启动预热消除首帧卡顿"与"内存占用"之间的取舍。


## 2026-10-14 "选了有道 OCR 却还在用 RapidOCR"（第四十九轮，v0.4.18）

### 现象
用户：「为什么我选择有道 OCR，结果是正在下载 RapidOCR」

### 诊断过程（先证实再改）
1. 读 `settings.json`：`ocr_engine = "rapidocr"`，而该文件 **5 分钟前刚被保存过** —— 说明保存动作发生了，但草稿里就是 rapidocr
2. 代码链：RapidOCR 的模型下载只存在于 `screenshot.rs` 的 `"rapidocr"` 分支（`rapidocr_ocr_pixels` → `ensure_ppocrv6_small_models`），走有道分支根本不碰它；且截图 OCR 用的是 `load_settings()`（读磁盘），未保存的草稿对它不可见
3. 枚举 settings.json 的写入方：`App.saveDraft`、截图窗口的 `selectEngine`/`applyLang`（都是先读盘再写回，不会回滚已保存的值）、主窗口关闭时的窗口尺寸回写（同样读盘再写）→ **没有任何路径能把已保存的 youdao 改回 rapidocr**
4. 写测试验证 UI：点击「有道 OCR」文字 → `onLocalChange` 调用次数 **0** —— 根因确认

### 根因
所有 `toggle-group` 行的结构是 `<div>` + 开关 `<label>`(44×24) + **平行的**文字 `<span>`。文字不在 label 里，**点文字没有任何反应**，只有精准点中那个小开关才生效。用户点的是文字 → 草稿没变 → 保存下去还是 RapidOCR → 首次使用触发模型下载。

### 修复
1. 10 处含开关的 `toggle-group` 整行容器由 `<div>` 改为 `<label>`，内层开关 `<label>` 同步改 `<span>`（避免 label 嵌套导致双重触发）；纯展示的「网络状态」行保持不动
2. `.toggle-group` 加 `cursor: pointer`

## 2026-10-14 截图模糊 + 原译同步 + 触发唤醒（第五十轮，v0.4.19）

### 1. 蒙版层出现后屏幕发虚（用户："我分得清暗和模糊的区别"）
- 根因：v0.4.10 为压触发延迟，把冻结快照改成 **1/2 降采样 + PNG**（`downscale_bgra(...,2)` + `win::encode_png`），前端 `object-fit: fill` 把这半分辨率位图拉回全屏。当时的判断是"识别仍用原始像素不受影响"——但用户看的是**底图**，观感就是整屏糊
- 实机参数：显示器 **2880×1800 @200% 缩放**（截图窗口物理尺寸与显示器一致，几何本身没问题）
- 修复：新增 `encode_snapshot_jpeg`，冻结底图改**全分辨率 JPEG(q85)**；JPEG 失败回退旧半分辨率 PNG
- 实测（`perf_snapshot_jpeg_encode`，2880×1800）：全分辨率 JPEG **109.2ms / 839KB**；旧半分辨率 PNG **33.1ms / 77KB** → 代价约 +76ms
- 取舍：清晰度是用户明确诉求，且「冻结画面」本身是设置开关——嫌慢可以关掉，换成实时屏幕（零编码开销且清晰）

### 2. 截图菜单「原/译」同步到覆盖层
- 此前 `copyMode` 只决定"复制什么"；现在覆盖块显示内容也随之切换：选「原」显示原文、选「译」显示译文
- 新增 `shownBlockText(block, copyMode)`，渲染与"渲染后字号收敛"逻辑共用同一份文本，并把 `copyMode` 加入该 effect 依赖，切换后字号会重算

### 3. "快捷键触发后要点一下鼠标才出选框"——两个确定性缺陷（第三个仍未证实）
- **缺陷 A（已修）**：实机 dump 截图窗口 `EXSTYLE=0x00040118`（APPWINDOW|WINDOWEDGE|ACCEPTFILES|TOPMOST）——**没有 `WS_EX_NOACTIVATE`、没有 `WS_EX_TOOLWINDOW`**，与《窗口行为守则》铁律不符。原因是 `SetWindowLong` 改扩展样式后必须补 `SetWindowPos(SWP_FRAMECHANGED)` 才生效，而 `main.rs` 里一直缺这一步
- **缺陷 B（已修）**：窗口长期停在屏幕外时 WebView2 renderer 可能被降级而不产帧。现在在窗口**仍在屏幕外**时先做一次 1px 尺寸变化强制重新布局产帧（代价为零，用户看不到），再归位 → show → focus → emit
- **仍未证实的部分**：本轮无法在无人值守下复现——模拟发送 LAlt+Q（keybd_event / SendInput 两种注入 + VK_MENU/VK_LMENU 两种变体）都没能触发截图窗口从 -32000 归位，因此无法自行观测"蒙版是否渲染"。已请用户复测；若仍复现，下一步加生命周期埋点（后端 trigger 各阶段时间戳 + 前端收到事件/rAF/首帧/首个鼠标事件）定位

### 4. 待办（用户确认加入）

- 若截图触发问题未根治：加上述生命周期埋点

## 2026-10-14 第五十一轮（v0.4.20）：NLLB 提速 + 5 项界面改进

### 待办1 · NLLB merged 解码器 + KV cache —— 已交付，1.9×
- **诊断门槛（先做后改）**：读代码发现 KV cache 能力是**从模型 I/O 通用推导**的（`past_key_values.*` 输入 ↔ `present.*` 输出），NLLB 之所以走慢路径**只是因为它加载的是非 merged 文件**。因此实现很小：
  1. `load_pair` 里 NLLB 也加载 `decoder_model_merged_quantized.onnx`（缺失自动降级到旧的 merged int8 → 非 merged）
  2. `(cache_flag_in, past_io)` 的推导去掉按家族的硬编码，改为"有 `use_cache_branch` 就按 merged 处理"
  3. `beam_decode` 与束重排改为按 `past_io.is_empty()` 分支，而不是按 `ModelKind`
- **实测对照（同机同 6 句，SMART_TRANSLATOR_MODELS_DIR 指向本地模型）**

| 句子 | 非 merged（旧） | merged（新） | 提速 |
|---|---|---|---|
| Mini Map and Mini Map test | 10.36s | 8.02s | 1.3× |
| Mini Map test | 2.76s | 2.04s | 1.35× |
| Hello world, this is a test. | 4.32s | 2.56s | 1.7× |
| The weather is nice today. | 3.88s | 2.32s | 1.7× |
| One or more mods caused the game to crash… | 8.25s | 4.09s | 2.0× |
| Please disable some mods and restart… | 8.35s | 4.68s | 1.8× |
| **6 句合计** | **44.8s** | **23.7s** | **约 1.9×** |

- **诚实结论**：未达计划里 4× 的预期。解码器确实从 O(n²) 变成 O(n)，但**编码器（600M 参数一次性前向）与 CPU matmul 占了剩余时间的大头**，短句尤其明显。译文基本一致（首句由"迷你地图和迷米地图测试"变为"小地图和小地图测试"，其余相同）

### 待办2 · q4 量化 —— **方案不成立，已如实撤销**
- 计划里"600MB→约300MB"是我的**推测**。实测查 hf-mirror 元数据：

| 文件 | int8 | q4 |
|---|---|---|
| encoder | 399.7 MB | **1095.7 MB** |
| decoder(merged) | 453.5 MB | **1126.8 MB** |
| 合计 | **0.85 GB** | **2.17 GB** |

- q4 导出反而**大 2.5 倍**，与"体积优先"的定位完全相反 → **不提供该选项**（避免误导下载 2.17GB）；后端保留 `nllb_variant` 字段与 q4→int8→非merged 的降级链，日后要实测 q4 速度可直接放开。已清理下载到一半的半成品 906MB
